# 多批次翻译管理方案 — 提炼与落地评估

> 来源：POPUP V2 交接包 handoff/03+04。本文把原始方案对照你当前平台(translation-server.js)实际已有的能力，标出**已有 / 缺口 / 建议**，供你决定要不要做、先做哪个。
> 原始方案全文见同目录 `原始方案_*.txt`。

---

## 一句话背景

你现在的平台擅长「**单任务**翻译流水线」(上传→A/B/C→分流→导出)。这套方案要解决的是「**项目级多批次管理**」——当一个翻译项目要拆成几十个批次、跨多语种、要追踪进度/成本/验收时，现在的单任务模型管不过来。

## 方案的核心设计(建议数据模型)

原始方案提出 6 张表，关键是前 3 个：

- **Project**：一个翻译项目，记录源表版本/哈希、目标语种、预算、审批状态
- **SourceRow**：每行一个 **row_uid**(不随排序变)，绑定 key/英文源文/source_hash/场景
- **Batch**：业务批次，含**不可变的 row_uid 列表** + 配置快照ID + 状态
- **BatchLocale**：批次×语种的任务，记完成/失败/待复核数 + 实际成本
- **ResultAttempt**：row_uid+locale+config_version+attempt 的 A/B/C 结果，幂等落库
- **Snapshot**：术语/DNT/知识库/Prompt/模型参数的冻结版本(不存明文Key)

批次状态机：`draft → ready → approved → running → needs_review → accepted`(+ failed/paused/cancelled)

## 开发优先级(方案建议的 P0/P1)

**P0(必做，否则多批次不可靠)**
- P0-01 数据导入与冻结：row_uid + 源哈希 + 空英文/冲突/非法JSON 阻断清单 + 只读源快照
- P0-02 Project/Batch/BatchLocale 模型 + 跨语种总览 + 操作前范围预览
- P0-03 配置版本冻结：运行中改术语不污染本批；长文本缺译不能标 completed
- P0-04 安全去重：禁止旧 `/api/dedup?apply=1` 对已翻任务删行；冲突预览+确认+可恢复
- P0-05 上线安全：可配置 PORT + 鉴权 + 持久化路径 + 单实例写约束

**P1(质量/成本/交付)**
- P1-01 试译验收门禁 + 母语审核放行记录(C高分/AI复核不能冒充人工批准)
- P1-02 持久化队列 + 幂等重试 + usage账本 + 预算硬停
- P1-03 术语维护:41候选逐项审定、172锁定抽检、来源/批准状态可追溯
- P1-04 跨批导出对账:全项目三语状态矩阵 + 完整性校验

## 我的落地评估(务实版)

### 这套方案值不值得做？
**分层看**。方案是"企业级"设计，全做工作量很大(6张表+状态机+队列持久化)。但你的真实痛点可能只是其中几块：

1. **最痛、最该先做的 3 件** (投入小、立刻止血)：
   - **row_uid 稳定标识**：现在靠 rowIndex，跨批/重排就错位(你之前踩过列错位的坑，同源问题)。加一列稳定 uid 成本低、收益大。
   - **配置版本冻结**：运行中改术语会污染在跑的批次。给任务存一份配置快照即可。
   - **长文本缺译不标 completed**：现在补翻跳过长文本后任务可能误标完成——这是正确性 bug，该修。

2. **中等价值、按需做**：
   - 持久化队列+幂等重试(P1-02)：你批量翻译规模大(单批2000+行)时，重启恢复和防重复扣费有用。
   - 跨批导出对账(P1-04)：多批合并交付时防错行/防漏语种。

3. **可以暂缓**：
   - 完整 Project/Batch 关系模型(P0-02)：除非你真要同时管几十个项目，否则现在的扁平 task 够用。
   - 鉴权(P0-05)：只要平台不暴露公网，内网用可以先不做(但别把 5051 直接暴露)。

### 建议的最小可行路径
先做 **row_uid + 配置快照 + 长文本completed修复** 这 3 个小改动——它们是正确性问题，不是功能扩张，风险低、都能加测试验证。等这些稳了，再看要不要上完整的 Project/Batch 模型。
